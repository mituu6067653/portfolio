# Meet Bhandari Portfolio — Rules

## 1. Core Rule
**Real work. Real information. No fake credibility.**

## 2. Never Invent
Do not invent:
- Clients
- Testimonials
- Revenue
- Years of experience
- User counts
- Awards
- Certifications
- Business results

Demo projects must be represented honestly.

## 3. Writing Rules
Use short, specific, human sentences.

Prefer:
> I build custom web applications for businesses.

Avoid:
> I leverage cutting-edge technologies to craft transformative digital experiences.

Prefer:
> This system manages production, inventory, quality and dispatch in one place.

Avoid:
> A revolutionary next-generation ecosystem for modern enterprises.

## 4. AI-Generated Feel
Do not use generic AI slogans, corporate buzzwords, fake testimonials, unnecessary 3D visuals, excessive gradients or animation-heavy template patterns.

## 5. Project Honesty
For every project:
- Explain what it actually does.
- Use its real deployment.
- Mention actual features.
- Do not claim real clients when it is a demo.
- Do not invent outcomes.

## 6. GitHub
Public repositories are optional.

If public:
- Clean README
- Setup instructions
- No secrets
- No `.env`
- Correct links

If private:
- Use the Live Demo as the primary proof.
- Do not make repositories public only for appearance.

## 7. Security
Never commit:
- Passwords
- API keys
- Database credentials
- Tokens
- Private client information

## 8. Contact Form
If implemented:
- Client validation for UX
- Server validation for security
- Message length limits
- Spam protection where practical
- Clear loading/success/error states

## 9. External Links
Every project link must be tested and point to the intended destination.

No placeholder URLs.

## 10. UI
Interactive elements need appropriate:
- Hover
- Focus
- Active/pressed
states.

Async operations need:
- Loading
- Success
- Error

## 11. Responsive
Test mobile, tablet, laptop and large desktop.

No horizontal overflow.

## 12. Typography
- Maximum two font families.
- Clear heading hierarchy.
- Readable line lengths.
- Comfortable line height.
- No tiny body copy.

## 13. Color
Use defined design tokens. Do not introduce random page-specific colors.

## 14. Animation
Animation must have a purpose, be fast and respect reduced motion.

## 15. Images
Use real project screenshots and a real personal photo if desired.

Do not use AI-generated portraits as if they are real.

## 16. Content Source
Keep repeated project/service information in centralized data to prevent inconsistent URLs and descriptions.

## 17. Dependencies
Before installing a package:
1. Is it needed?
2. Can the existing stack solve it?
3. Is it maintained?
4. Does it add meaningful value?

## 18. Performance
Avoid:
- Huge videos
- Unoptimized screenshots
- Heavy animation libraries
- Excessive client JavaScript
- Autoplay media

## 19. SEO
Write metadata for humans first. No keyword stuffing.

## 20. Git Commits
Good:
- `feat: add featured projects`
- `feat: add contact form`
- `fix: correct project links`
- `ui: improve mobile navigation`

Bad:
- `update`
- `changes`
- `final`
- `final2`

## 21. Final Test
Open the website as a stranger and ask:

> Would I trust this person enough to message them about my business website?

If not, improve clarity and proof before adding features.
